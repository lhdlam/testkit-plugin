testkit — AI tự viết bộ test automation

Triết lý: agent viết & bảo trì test, Playwright/pytest chạy test. Bạn (tester) là người gác cổng: ở mỗi pha bạn review artifact rồi mới cho agent đi tiếp. Quy trình đi qua 6 pha, mỗi pha kết thúc bằng một artifact + một điểm review của con người.

Dùng sidebar bên trái để chuyển trường hợp sử dụng, hoặc click từng bước (step) để nhảy nhanh. Mỗi bước có Tại sao · Bạn làm · Bạn thấy để người mới follow được.

Trước khi bắt đầu & cài đặt plugin

testkit chạy trên Claude Code (gate cưỡng chế) và Cursor (gate advisory). Agent viết test; framework chạy test trỏ tới URL môi trường deploy (Staging/UAT) — testkit không dựng app ở local.

Phiên bản hiện tại hiện thực đầy đủ 2 target: web-playwright (web app, test trỏ URL Staging/UAT) và desktop-pyside6 (app PySide6, test in-process bằng pytest-qt). Hướng dẫn chính đi theo ví dụ web; xem UC2 cho desktop.

0. Cần chuẩn bị

  • Claude Code (hoặc Cursor) cài plugin testkit.
  • Node.js 18+ (node --version).
  • URL môi trường deploy: STAGING_URL (và UAT_URL nếu có). testkit KHÔNG dựng app ở local.
  • Tài khoản test riêng cho automation trên Staging (tách khỏi tài khoản người thật).
  • (Khuyến nghị) Playwright MCP để agent mở Staging xác thực selector. KHÔNG cần để chạy test — chỉ để agent tìm/verify selector. Bắt buộc cho web-from-docs/web-blackbox, khuyến nghị cho web-playwright, không dùng cho desktop. Cài nhanh: /testkit:mcp.

Mô hình tinh thần: 6 pha, mỗi pha 1 cổng review

6 pha giống nhau cho mọi nền tảng; khác biệt gói trong profiles/<target>.md. Mỗi pha tạo ra một artifact và có một điểm review của con người trước khi sang pha sau.

Pipeline Từ init đến CI — 🚦 = bạn review trước khi sang pha sau

testkit · 6-phase pipeline
/testkit:init Phase 0 Setup: scaffold + CLAUDE.md + config (không cần review) │ /testkit:analyze Phase 1 Hiểu app → feature-map.md 🚦 bạn review │ /testkit:cases Phase 2 Sinh test case + rtm.md 🚦 bạn review │ /testkit:scenarios Phase 3 Map selector thật + kịch bản E2E 🚦 bạn review │ /testkit:script Phase 4 Sinh Page Object + *.spec.ts + auth 🚦 bạn đọc assertion │ /testkit:run Phase 5 Chạy + phân loại fail + self-heal (lặp tới khi xanh) │ /testkit:ci Phase 6 Sinh workflow CI (xong)

Pipeline đầy đủ (web-playwright) — ví dụ module Login

Đi trọn 6 pha cho một web app: agent đọc code → hiểu app → sinh test case → map selector thật → sinh test code Playwright (TypeScript, Page Object) → chạy & tự chữa → sinh CI. Test trỏ URL Staging/UAT; auth đăng nhập 1 lần rồi tái dùng phiên.

Bắt đầu nhỏ: làm trọn module login (analyze → … → run xanh) trước khi nhân rộng. Vừa kiểm chứng quy trình, vừa cho agent một "mẫu" để bắt chước cho các module sau.

Công cụ tester hàng ngày — đọc tài liệu · viết test case · nghiệm thu dev

Ba lệnh dùng ngoài pipeline, cho công việc hằng ngày của tester: hỏi đáp có trích dẫn (/testkit:question), sinh script theo test case (/testkit:tc), và nghiệm thu output của dev theo test case (/testkit:review-dev).

Dual-input (tài liệu + code): khi project có cả 2 nguồn, /testkit:analyze dùng tài liệu làm nguồn YÊU CẦU (REQ-xxx) và code làm nguồn HIỆN THỰC, rồi cross-check hai chiều: chỗ "Tài liệu ≠ Code" được ghi vào open-questions.md (bug tiềm ẩn hoặc tài liệu lỗi thời) cho con người phân xử trước khi sinh test case.

Q&A /testkit:question — trả lời KÈM reference

question · không nguồn = không khẳng định
▶ Bạn hỏi $ /testkit:question mật khẩu yêu cầu tối thiểu bao nhiêu ký tự? ▼ Agent trả lời — mọi ý khẳng định kèm nguồn Tối thiểu 8 ký tự, ≥1 số và 1 ký tự đặc biệt [SRS.docx §3.4 "Password policy"]. Đã cover bởi [test-cases.md → Register / mật khẩu dưới 8 ký tự bị từ chối]. ⚠ Code hiện chỉ check độ dài ≥8 [app/validators.ts:31] — lệch tài liệu → đề xuất ghi open-questions.md. ▼ Quy tắc · Tra theo thứ tự: tài liệu → artifacts (test-cases/rtm…) → code → test code · Không có trong nguồn → nói thẳng "tài liệu không đề cập", KHÔNG suy diễn · Mâu thuẫn giữa nguồn → nêu cả 2 phía kèm reference, để con người phân xử

TC → script /testkit:tc — automate đúng case bạn chọn

tc · gate: test-cases.md APPROVED
▶ Chỉ định test case (theo module hoặc tiêu đề) $ /testkit:tc Login $ /testkit:tc "đăng nhập thất bại khi sai mật khẩu" ▼ Agent làm gì 1. Trích Steps/Expected/Precondition của TC từ test-cases.md (phải APPROVED) 2. Resolve selector THẬT: ui-map.md → hoặc khám phá qua Playwright MCP / objectName (KHÔNG đoán) 3. Tái dùng Page/Screen Object; thêm 1 test / case, tên test = tiêu đề case (không comment) 4. Chạy thử đúng test đó: npx playwright test -g "đăng nhập thất bại khi sai mật khẩu" 5. Đánh dấu [automated] vào rtm.md → theo dõi tiến độ automate theo case ⚠ Hành vi thật khác Expected Result → KHÔNG bẻ assertion theo sản phẩm, ghi bugs.md.

Nghiệm thu /testkit:review-dev — review output dev theo test case

review-dev · dùng được cả khi CHƯA automate
▶ Dev bàn giao tính năng → nghiệm thu theo scope $ /testkit:review-dev login # hoặc tiêu đề một test case ▼ Agent đi qua TỪNG test case trên sản phẩm thật · web: Playwright MCP mở Staging, làm đúng Steps, so với Expected Result · desktop: đọc code bàn giao + quick check pytest-qt · TC đã [automated] → chạy script thay vì thao tác lại ▼ Verdict từng TC → dev-review-login.md ✅ Pass hành vi khớp Expected Result ❌ Fail lệch Expected → ghi chi tiết + bugs.md (repro, expected vs actual) ⛔ Blocked không đi tới được bước test (lỗi khác chặn / thiếu data) ⚠ Untestable UI/flow thực tế khác test case → cập nhật case hoặc hỏi lại Tổng: N case — X Pass / Y Fail / Z Blocked / W Untestable ⚠ KHÔNG hạ Expected Result cho khớp sản phẩm — đó là quyết định của tester/BA. ▼ Sau nghiệm thu Fail → dev sửa → chạy lại đúng các TC đó · Pass đủ → /testkit:tc để automate case chưa có script

Chẩn đoán & sửa bug — /testkit:fixbug

Từ mô tả 1 bug (hoặc tiêu đề một mục đã có trong bugs.md): agent định vị nguyên nhân gốc trong code + tài liệu (kèm reference), hỏi bạn những gì còn mơ hồ, rồi sửa code app và luôn để lại 1 regression test tái hiện bug (đỏ trước fix, xanh sau).

⚠️ Đây là command DUY NHẤT của testkit chạm vào code sản phẩm (mở rộng có chủ đích sang dev-side). An toàn nằm ở human gate bắt buộc: agent DỪNG lại hỏi bạn + trình hướng sửa, và không sửa một dòng code nào trước khi bạn duyệt. Vẫn cấm green-washing: sửa app cho test xanh, KHÔNG làm yếu test.

dev-side human gate regression test không cần test-cases APPROVED

Đầu vào mô tả tự do hoặc tiêu đề mục trong bugs.md

Luật vàng · lệnh nhanh · sự cố thường gặp

Luật vàng Đừng phá

7 luật vàng
1. KHÔNG green-washing. Test đỏ vì app sai → đó là test làm đúng việc. Đừng để agent "sửa test cho xanh". Quy ước này nằm sẵn trong CLAUDE.md; thấy agent định làm yếu assertion → DỪNG. 2. Dữ liệu tự sinh, tự dọn. Staging dùng chung → mỗi test tạo dữ liệu riêng (email có timestamp), không đụng dữ liệu người khác. Flaky do data drift chữa bằng cách này, KHÔNG bằng tăng timeout. 3. Code sạch để bàn giao khách. Code sinh ra KHÔNG comment (không comment truy vết/giải thích, không dấu ngày, không tên khách) và KHÔNG mã định danh tự đặt (TC-xx, REQ-xx, BUG-xx, OQ-xx). Test case nhận diện bằng Module + tiêu đề mô tả; tên test CHÍNH LÀ tiêu đề đó. Truy vết sống trong rtm.md, không nhúng vào code. Trích dẫn nguồn thật (SRS §4.2, file:line) vẫn giữ — trong TÀI LIỆU, vì đó là tham chiếu có thật, không phải mã bịa. 4. NGHIÊM CẤM comment tiếng Việt trong code. Không ngoại lệ. Tài liệu/artifact vẫn viết tiếng Việt theo lang — CODE thì không. 5. Không che lỗi bằng suppression. Cấm gắn # noqa, # type: ignore, // @ts-ignore, // eslint-disable… để làm xanh lint. Gặp cái có sẵn → XOÁ rồi sửa nguyên nhân thật; không sửa được thì báo người, KHÔNG che. Che lỗi bằng suppression = green-washing. 6. Không ghi quyết định của khách vào code. Cấm comment kiểu // khách chốt bỏ validate — 02/10/2026, # theo yêu cầu KH ngày 15/9, tên khách, số hợp đồng/ticket. Quyết định nghiệp vụ thuộc về TÀI LIỆU, không phải code. 7. Dọn rác khi gặp (cleanup-on-sight). Khi làm tính năng mới / sửa bug, thấy mã định danh cũ (TC-xx, REQ-xx, BUG-xx, OQ-xx), comment tiếng Việt, comment thừa, ghi chú quyết định của khách + ngày, hay chỉ thị tắt lint (noqa / ts-ignore / eslint-disable) ở BẤT KỲ đâu → XOÁ NGAY trong cùng lần sửa. Không giới hạn phạm vi, không hỏi lại, không để "dọn sau".

  • coverage-auditor — dựng/kiểm RTM, báo yêu cầu chưa có test.
  • failure-classifier — phân loại mỗi fail (Bug | Selector | Timing | Data | Env | Doc-drift), route bug → bugs.md.
